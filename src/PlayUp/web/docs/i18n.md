# Play'Up Web — Internationalization (i18n)

Phase 14.8.2+ foundation: [i18next](https://www.i18next.com/) + [react-i18next](https://react.i18next.com/).

## Why

Play'Up must support multiple locales over time and must stop accumulating hardcoded UI strings. The default product locale is **`fr`**. English resources can be added later under `src/i18n/locales/en/` without changing the init pattern.

## Backend / frontend string strategy (closed)

> **Backend = codes + structured facts + English diagnostic messages.**  
> **Frontend = all organizer-facing copy via i18next.**

| Belongs on the wire | Does **not** belong on the wire |
| :--- | :--- |
| Stable machine codes (`PrepareStage`, `DrawNoSolution`, `Application.StageNotFound`, …) | Organizer labels / reasons / hints in FR or EN |
| Structured facts (counts, ids, enum wire values, `Facts`) | Dimension / action / progression prose |
| Business data (`name`, `displayName`, stage names) | Hardcoded UX sentences in Application assemblers |
| Exception **Detail** in English (diagnostic / support) | Product chrome copy |

There is **no** .NET `IStringLocalizer` / `.resx` / `Accept-Language` for V1. Translation keys **are** the wire codes; the client maps `code → t(key)`.

**Overview Read** and other organizer reads expose **codes + facts only** (no FR/EN prose fields). Translation keys **are** the wire codes; the client maps `code → t(key)`.

Host HTTP notes: [http-api-contract.md](../../../../docs/guides/http-api-contract.md). Notion SoT: Internationalisation (Expérience produit).

## Rule

From phase 14.8.3 onward:

> **Every new user-facing or accessibility string must go through i18n.**

Exceptions:

- Business data from the API (`competition.name`, `displayName`, …)
- Brand marks (`PLAY'UP`, `Play'Up`)
- Technical identifiers (GUIDs, route paths, enum **wire values** in API payloads, API codes shown in `mono`)
- Logs and developer-only copy

Never use business data as an i18n key.

## Layout

```text
src/i18n/
├── index.ts          # init + document.lang sync
├── config.ts         # DEFAULT_LOCALE, namespace list
├── enumLabels.ts     # wire code → label helpers (enums namespace)
├── actionLabels.ts   # action / progression codes → labels
├── situationCopy.ts  # attention / situation sources → copy
├── apiErrorLabel.ts  # ProblemDetails code → errors namespace
└── locales/fr/
    ├── common.json   # cross-cutting UI + a11y (loading, errors, skip link)
    ├── shell.json    # shell chrome (sidebar, header, attention drawer)
    ├── enums.json    # status / enum labels + attention codes
    ├── actions.json  # semantic action / progression labels
    ├── overview.json  # Overview chrome + dimension templates
    ├── matches.json
    ├── draw.json
    ├── organisation.json
    ├── stage.json
    ├── home.json
    ├── competitions.json
    ├── classements.json
    └── errors.json
```

Add a namespace by:

1. Creating `locales/fr/<namespace>.json`
2. Registering it in `I18N_NAMESPACES` (`config.ts`) and `resources` (`index.ts`)
3. Using `useTranslation('<namespace>')` in components

## Usage

```tsx
import { useTranslation } from 'react-i18next'

function Example() {
  const { t } = useTranslation('shell')
  return <button>{t('competition.change')}</button>
}
```

Enum/status labels — **wire code stays unchanged on the API**; user labels come from `enums`:

```tsx
import { matchStatusLabel } from '../i18n/enumLabels'

matchStatusLabel('Running') // → "En cours" (fr)
// i18n key: enums:matchStatus.Running
```

Actions / situations (same pattern):

```tsx
import { actionLabel } from '../i18n/actionLabels'
import { situationTitle } from '../i18n/situationCopy'

actionLabel('PrepareStage', { name: stageName })
situationTitle('DrawNoSolution')
```

Pattern: **wire code → i18n key → user label**. Unknown codes fall back to the wire value (`defaultValue`).

API errors: `ProblemDetails.code` → `errors:<code>` via `apiErrorLabel`; English `detail` only as diagnostic fallback when the code has no translation.

Pluralization (French — native i18next suffixes):

```tsx
const { t } = useTranslation('shell')
// count 0 → trigger_zero, 1 → trigger_one, 2+ → trigger_other
aria-label={t('attention.trigger', { count })}
```

Key conventions:

- Semantic keys, not French prose (`competition.change`, not `changer`)
- One key = one product meaning
- Named interpolation (`{{count}}`, `{{name}}`, `{{status}}`)
- No concatenation of translated fragments

## Accessibility

`aria-label`, button labels, navigation names, and skip links are **user-facing** and must use i18n like visible text.

## Tests

```tsx
import { renderWithI18n, I18nTestProvider } from '../test/renderWithI18n'

renderWithI18n(<MyComponent />)
```

Vitest setup wraps all renders with `I18nTestProvider` (locale **`fr`**). Prefer `getByRole` with accessible names; do not assert every translation key.

## Not i18n

Date, time, number, and currency formatting stay with the platform **`Intl`** APIs (`Intl.DateTimeFormat`, `Intl.NumberFormat`) using the active locale.

## Lint

No custom AST lint — the rule is enforced by convention, code review, and this document.

## Page migration

When reworking a legacy 13.5 page, also follow [page-migration.md](./page-migration.md) (Design System classes + i18n + `queryKeys`).

Priority when a product task touches the page: Workspace → Match hub → Stage / `drawUi` → Organisation.

## Out of scope (V1)

- English locale files and language selector
- Host `Accept-Language`
- Mass migration of every page for i18n alone
- Frenchifying Domain / Application exception messages
